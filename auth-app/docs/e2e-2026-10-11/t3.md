### D1 (S2) Import of Personal candidates ignores existing organisation rows with the same email
- Repro: as `t3.j1@t3-co.io` in Personal add "Olga Orgonly" with email `olga.orgonly@t3cand.example` (the org already has that
  person, owned by the owner, on a campaign j1 can see). Join T3 Co (direct). `GET /v1/organisation/import-personal` says
  `candidates: 4` (Olga included); `POST /v1/organisation/import-personal` copies 4. `tenant_t3_co.candidates` now has two rows
  with that email and two different `person_id`s (owner's and j1's). Same for a hidden candidate: `t3.j2` imported
  "Hector Imported Dup" with the email of a candidate j2 cannot see (LinkedIn matches were excluded, email matches were not).
- Expected (workspaces-and-orgs.md section 1 and 2): offered "only while they have some that the organisation does not";
  typing the same email says "already saved by your team".
- Actual: the offer counts them and the copy creates a duplicate; matching is by pool `person_id` only, and a typed person in
  Personal is a different pool person.
- Guess: `public.import_personal` / `public.personal_import_offer` (migration 179): compare normalised email and phone (as
  `findInWorkspace` does for typed adds), skip or link.

### D2 (S2) Wrong "removed" message when the person switched workspace elsewhere
- Repro: `t3.rec2` open on `#/contacts` in T3 Co; from another tab or `POST /v1/workspace/active {organizationId:null}`; click any
  page in the first tab. Also API: active = Personal, `x-workspace: <T3 Co id>` on any write.
- Expected: 409 "Your workspace changed." (the middleware's own intent: "Another tab switched").
- Actual: 403 `{removed:true, workspaceChanged:true}` "You're no longer a member of that workspace." and the tab says "You're no
  longer a member of that workspace. You're in your own workspace now." to a person who is still a member.
- Guess: `platform/http.ts` `withScope` calls `core.was_member`, which is true for current members too (it checks `users` row
  existence, any status); it must mean "was, and is not now".

### D3 (S2) Recruiter sees false placeholders on Clients
- Repro: owner sets Industry "Fintech" on a client with a contact; `t3.rec1` (on a campaign of that client) opens Clients and the
  client. `GET /v1/clients` for rec1 returns `industry: "Fintech"`, `ownerName`, `primaryContact`.
- Expected: those fields (fee, notes and activity stay hidden).
- Actual: row "Not set / Not set / No contact yet / Unassigned", detail "Client since Not recorded, Industry Not set, Account owner
  Unassigned"; the line "Your admins look after clients..." sits jammed against the panel divider (layout).
- Guess: `campaignStore.ts` `rebuildClients()`: "A recruiter can't list clients, but their campaigns still name theirs" builds
  clients from campaigns (id and name only); the list call is skipped or ignored for recruiters.

### D4 (S2, conditional on exposure) Row level security does not apply roles or visibility
- Repro (psql, `set local role authenticated`, claims `sub` = `t3.rec2`, rolled back): `select count(*) from
  tenant_t3_co.candidates` = 11 (API: 4); campaigns 7 (API: 2); `clients` 5 rows with fee and notes; `update
  tenant_t3_co.clients set notes='x'` = 5 rows; `delete from tenant_t3_co.candidates where full_name like 'Olivia%'` = 1 row;
  `core.runs` = 24 rows, 16 of them other people's chats, `core.run_events` = 204.
- Expected: agent-architecture.md "Enforced in the DB with row-level security... A frontend bug can't leak another campaign";
  workspaces-and-orgs.md says the rule is also in SQL.
- Actual: all 37 tables of the tenant schema carry one policy, `core.is_member(<org>)`, for read and write; `runs_read` and
  `run_events_read` are org-wide. Cross-tenant and Personal policies (`workspace_owner = auth.uid()`) are right (0 rows across
  tenants, insert as someone else refused). The API connects as superuser, so only a direct database path (a tenant schema or
  `core` exposed to PostgREST, any `authenticated` connection) is affected; open decisions 1 and 5 in the audit.
- Guess: the policy generator `core.ensure_policy` bodies in migrations 102 and 179; add role and `candidate_visible` aware
  policies, or revoke `authenticated` table grants on tenant schemas and `core.runs`.

### D5 (S2) Invite refuses free-mail, ask-to-join accepts it
- Repro: owner or admin `POST /v1/members/invites {email:"t3.k2@gmail.com"}` -> 403 "Personal email addresses can't join
  organisations." Then `t3.k2@gmail.com` `POST /v1/organisations/<T3 Co>/join` -> requested; admin approves; k2 is a recruiter.
- Expected: one rule (section 3 allows personal-address people to join by request; an organisation made from a personal address
  has no domain and can only be reached by invitation or request).
- Actual: an owner on free-mail cannot invite colleagues on free-mail; the message is untrue.
- Guess: `public.invite_member` `core.is_free_domain(...) and not core.is_email_allowlisted(...)` check (pre-179 rule).

### D6 (S2, confirm intent) Applicant "Add" duplicates a held person
- Repro: publish a form on a campaign `t3.rec2` can see; an applicant with `helga.hiddentwo@t3cand.example` (held by the owner,
  hidden to rec2) submits; rec2 opens Responses (possible match correctly empty) and clicks Add.
- Expected: "already saved by your team" like typing, or one row.
- Actual: 200 "added", a second candidate (new person, owner rec2, source form) with the same email now sits beside the owner's.
- Guess: `forms/service.ts` decision "add" path does not run the hidden-duplicate check that `addCandidate` does.

### D7 (S2/S3) Shared pool exposes typed names
- Repro: `t3.out` (other tenant) as `authenticated`: `select full_name from mother_data.people where full_name in ('Penny
  Personalonly','Olivia Ownerline','Oscar Outsiderperson')` returns all (Penny is a Personal-workspace candidate typed by the
  owner; all `discoverable = true`, no LinkedIn needed). `select public.extension_lookup('<linkedin of a typed candidate>')` as
  another tenant returns `full_name`; `extension_save` as a recruiter wrote `current_title` into the undescribed pool row of a
  person the owner holds (rolled back), so any signed-in user can fill an undescribed pool person first.
- Expected: Personal is "private to the person"; tenant-typed data is not findable by other tenants (audit findings 6, 8, 9).
- Actual: typed names and LinkedIn URLs enter the pool as discoverable. Reachable by the extension functions; by direct select only
  if `mother_data` is exposed (audit open decision 5).
- Guess: pool insert for manual/import/typed adds should set `discoverable=false` until a consenting or sourced source;
  migrations 174/175.
