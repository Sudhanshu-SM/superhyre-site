SuperHyre agent architecture

The System and Memory tabs are the plan as of 4 Oct 2026, from docs/agent-architecture.md. The Agent flow (built) tab shows what runs today. Orange is the numbered request path; grey is the extension and side paths.

1 · High-level design

One Railway app (API, worker, memory module) sits between the console and Supabase. Supabase holds the records; Redis and Qdrant hold cache and memory so the main database does no memory work.

  1. 1Sign in. Google sign-in through Supabase Auth gives the console a JWT.
  2. 2Request. A chat message or button goes to the API with the JWT.
  3. 3Check and queue. The API checks role and campaign membership, writes a run row (queued) and answers at once with its id.
  4. 4Claim and write back. The worker claims the run (FOR UPDATE SKIP LOCKED), and later writes results, records and run_events.
  5. 5Context. The orchestrator asks the memory module for one context bundle.
  6. 6Memory stores. Profiles and the chat's observation log from Redis; filtered and hybrid recall from Qdrant. Learning writes go back the same way.
  7. 7Model. Prompt in 8 fixed layers to Claude: Sonnet for every step, through our claude-code-gateway.
  8. 8Data providers. Crustdata search (≤ 20 new per run), Apify profile fetches, and message sending.
  9. 9Changes. Every write in Postgres is published by Supabase Realtime.
  10. 10Live events. The console streams progress, questions, results and approval requests.
  11. 11Candidate. Outreach, replies and form links over WhatsApp or email, always after approval.
  12. 12Webhooks. Replies and form submissions come back to the API as triggers.
  13. E1Extension save. The sidebar saves a profile through an RPC (unchanged).
  14. E2Find contact. The sidebar asks the edge function for a number (unchanged).
  15. E3Contact chain. SalesQL → ContactOut → Apollo, with per-org credits (unchanged).
  16. AArchive. Raw sessions, transcripts and provider payloads go to Storage, not the database.

2 · Orchestrator: every trigger, same eight steps

Code, not one big agent. Buttons and webhooks are routed by a table; only free-text chat goes to the small router model. Each skill declares the context it needs.

3 · Sourcing and matching

Narrow and cheap first, careful last. 20 new people on the first search, then 10, then 5 per find more; never anyone already held or already shown in this campaign.

4 · Memory: write path and read path

Writes happen in the background from events. Reads happen once per turn through getContext and end in a fixed prompt order so most of each prompt is cached.

5 · Candidate data: one door in, Apify fills the rest

Every route into the pool uses the same ingest and dedupe. A LinkedIn URL is enough for Apify to fill skills, experience and education; recruiter-typed fields always win.

0 · How the agent reads and writes memory (built)

What happens on every chat turn, and what happens afterwards. Reads never fail a turn: if memory is down, the agent answers with nothing remembered. Writes are queued and retried.

  1. 1Ask for context. The run engine gives the memory module the message, the campaign and the client.
  2. 2Embed. The question is turned into a dense and a sparse vector.
  3. 3Profile. Lasting facts, preferences, beliefs and playbooks for this scope, strongest first.
  4. 4Recall. The memories closest to this message, found by meaning and by exact words together.
  5. 5Return. At most 20 profile items and 6 recalled ones, with duplicates removed.
  6. 6Into the prompt. They appear as “Remembered:” lines the model is told to treat as history, never as instructions.
  7. W1Save on request. “Remember that Acme never…” makes the model call remember, which queues a write.
  8. W2Distil. Ten quiet minutes after a chat, the worker reads the new messages.
  9. W3Extract. Haiku returns at most eight memories, usually none.
  10. W4Write. The memory module embeds, checks the rules, then creates, reinforces or replaces a memory.

1 · Where everything lives

Two kinds of memory sit side by side. Records (people, candidates, reveals, credits) are in Postgres and are exact. Agent memory (what the agency has told the agent, what happened on past work) is in Qdrant and is searched by meaning. Nothing in Qdrant holds a phone number or email.

2 · Agent memory: kinds, levels, write and read

KindWhat it isWritten byIn the turn's profile
factStated plainly: "Acme never takes notice periods over 60 days"remember tool, distillationYes, ranked by confidence
preferenceHow someone likes things: shortlist size, tone, locationsremember tool, distillationYes
beliefA pattern inferred from several signals; starts at confidence 0.6distillationYes
playbookA way of working worth repeatingremember tool, distillationYes
episodeSomething that happened: a sourcing run, a candidate turned down with a reasonsourcing, matchingNo, found by recall
exampleAn approved role spec, the starting point for similar rolesspec approvalNo, found by recall

Levels: org (the whole agency, or the personal workspace), client, campaign, recruiter (one person's own preferences) and candidate (episodes about one person, tagged with person_ids). The workspace key is the organisation id, or personal:<user id> for someone working alone.

1 · The system, built

One chat message, from the box to the screen and back. The run engine, tool server and worker are one process locally (ROLE=all). Chat turns do not wait for the worker.

  1. 1Send. The console posts the message with a client id, so a resend is the same message.
  2. 2Run row. One lock per client id, a free run slot, then the quotas. Then a run is stored.
  3. 3Answer at once. The API replies 202 with the run id. The console opens its stream.
  4. 4Hand over. The run engine takes the turn. Turns in one chat run one after another.
  5. 5Context. The run engine asks the memory module for what the agency told the agent.
  6. 5bEmbed. The question becomes two vectors, dense and sparse, by the gateway.
  7. 6Recall. Two ranked reads on Qdrant, always filtered to this workspace.
  8. 7Prompt. Fixed system prompt, a context block for this turn, and a signed key for tools.
  9. 8Model. The gateway runs Claude Haiku with the tool list.
  10. 9Tools. The model calls back into our /mcp with that key. Workspace and person come from the key, never from the model.
  11. 10Lookup. The tool reads the data and saves a card as an event.
  12. 11Events. Words, cards and the finish are written as run events.
  13. 12Live. Postgres notifies, the stream pushes, the console draws each event.
  14. W1Remember. A queued job writes the memory to Qdrant.
  15. W2Distil. After a chat is quiet for 10 minutes, Haiku pulls lasting facts out of it.
  16. W3Reach out. Search, profile fetches and sending, only after approval.

2 · What the chat box is made of

Every kind of thing the agent can put in a chat. Each one is an event on the run, drawn by one console component. A reopened chat replays the same events, so the cards come back.

3 · How the agent decides

Code goes first because model calls are the scarce resource here. The model is only asked when words alone cannot decide.

4 · The worker

The worker runs background jobs, not chat. A job is a row in Postgres (pg-boss), so a restart loses nothing. Locally the API and the worker run in one process (ROLE=all).
